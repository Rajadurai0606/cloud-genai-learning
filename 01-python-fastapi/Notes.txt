Employee Lookup

HTTPException

    HTTPException should be raised, not returned.

    This stops normal processing and FastAPI returns an HTTP error response.


HTTP Status Codes used

    200 OK

    201 Created

Day 8 - Docker Container Lifecycle and Layer Caching


Docker Image vs Container

    Image:
        A packaged blueprint/template used to create containers.

    Container:
        A running instance created from an image.

    Simple understanding:

        Dockerfile
            -> docker build
            -> Image
            -> docker run
            -> Container

    One image can be used to create multiple independent containers.

    Simple analogy:
        Class  -> Image
        Object -> Container

    This is only an analogy to help remember the concept.


Image and Container Lifecycle

    docker build
        Creates an image from the Dockerfile.

    docker run
        Creates a new container from an image and starts it.

    docker stop
        Stops a running container.
        The container still exists.

    docker start
        Starts an existing stopped container.

    docker rm
        Removes the container.

    Removing a container does NOT remove its image.

    The same image can be used again to create another new container.


Useful Container Commands

    docker ps
        Shows only running containers.

    docker ps -a
        Shows all containers, including stopped containers.

    docker stop <container-name>
        Stops a running container.

    docker start <container-name>
        Starts an existing stopped container.

    docker rm <container-name>
        Removes a stopped container.

    docker ps --filter "name=<container-name>"
        Filters containers by name.


Naming a Container

    A container can be given our own meaningful name:

        docker run --name cn-my-fastapi -p 8001:8000 my-fastapi:latest

    If we do not provide a name, Docker automatically generates one.


Port Mapping

    Example:

        -p 8001:8000

    Means:

        Host/Windows port 8001
                ->
        Container port 8000

    Therefore the FastAPI application running on port 8000 inside
    the container can be accessed from:

        localhost:8001


Docker Layer Caching

    Docker builds the image step by step and remembers (caches)
    previous build steps.

    Example build order:

        1. Use Python base image
        2. Copy requirements.txt
        3. Install dependencies
        4. Copy application code

    If we later change only main.py:

        Python base did not change       -> reuse cache
        requirements.txt did not change -> reuse cache
        dependencies did not change     -> reuse cache
        application code changed        -> rebuild this part

    This is why we copy requirements.txt and install dependencies
    BEFORE copying the application code.

    requirements.txt changes rarely.
    Application code changes frequently.

    If we copy the whole application first, even a small change to
    main.py can cause the later dependency installation step to run again.

    Simple understanding:

        No change -> Docker can reuse cached work
        Change    -> Docker rebuilds from the affected step onward

    Benefit:
        Faster Docker builds and avoids reinstalling dependencies
        unnecessarily.


Docker Image Optimization

    Initially used the full Python base image and the FastAPI image
    was over 1 GB.

    Changed to the Python slim base image and reduced the image size
    to approximately 342 MB.

    Smaller base images can reduce image size and unnecessary content.

    No further image-size optimization is required at this stage.


Practical Exercise Completed

    Verified running containers using docker ps.

    Verified running + stopped containers using docker ps -a.

    Started an existing stopped container.

    Stopped the container.

    Removed the container.

    Confirmed that removing the container did not remove the image.

    Created a new container from the same my-fastapi image.

    Named the new container cn-my-fastapi.

    Mapped host port 8001 to container port 8000.

    Verified the FastAPI /health endpoint successfully from:

        localhost:8001/health


Important Learning

    Image and container have separate lifecycles.

    Stopping a container:
        -> container still exists
        -> image still exists

    Removing a container:
        -> container is deleted
        -> image still exists

    Removing the image:
        -> removes the image itself

    As long as the image exists, we can use it to create new containers.

    Docker caching makes repeated builds faster by reusing unchanged
    build steps.

Day 9 — GCP Fundamentals and Configurable Application Port

GCP Basics

- Project: A boundary for organizing cloud resources, permissions and costs. Separate projects can be used for dev, test and production. Organizations and folders can sit above projects.
- Region: A geographical area, such as europe-west2.
- Zone: A deployment area within a region, such as europe-west2-a. A region contains multiple zones.

Artifact Registry, Cloud Run and GKE

- Artifact Registry stores built container images so deployment services can access them.
- Cloud Run runs containerized applications while Google manages the underlying infrastructure and scaling.
- GKE provides managed Kubernetes for workloads needing Kubernetes features and greater control.
- Choosing Cloud Run or GKE depends on workload and control requirements, not simply application size.

Our deployment path:

    Code → docker build → Image → Artifact Registry → Cloud Run or GKE


Configuring the Application Port

```python
import os
import uvicorn

if __name__ == "__main__":
    port = int(os.getenv("PORT", "8000"))
    uvicorn.run("app.main:app", host="0.0.0.0", port=port)
```

- os.getenv reads an environment variable.
- If PORT is missing, the application uses 8000.
- Environment-variable values are strings, so int() converts the port to a number.
- 0.0.0.0 makes the server listen on all container network interfaces.
- Environment variables let us configure the same image without changing code or rebuilding.
- Cloud Run supplies PORT; our application must listen on that port.


Docker Startup Command

```dockerfile
CMD ["python", "-m", "app.main"]
```

- -m runs app.main as a Python module, allowing its relative imports to work.
- Use app.main, without the .py extension.
- The __main__ guard starts Uvicorn only when the module is executed as the entry point.
- When Uvicorn imports app.main, the guarded startup block does not run again.


Application Port versus Docker Port Mapping

These are separate settings:

    PORT environment variable
        → Our code uses it to choose where Uvicorn listens.

    -p HOST_PORT:CONTAINER_PORT
        → Docker forwards host traffic to a container port.

The -p option does NOT set the application's listening port.
The container port in the mapping must match where the application listens.


Test 1 — Default Port

```powershell
docker run --rm -p 8001:8000 im-employee-api-1
```

- No PORT environment variable supplied.
- Python uses the default: 8000.
- Docker forwards host 8001 → container 8000.
- http://localhost:8001/health returned a healthy response.


Test 2 — Overridden Port

Contents of .env:

```text
PORT=5000
```

Command:

```powershell
docker run --name cn-employee-api-1 --env-file .env -p 8080:5000 im-employee-api-1
```

- Docker reads .env and supplies PORT=5000 to the container.
- Python reads PORT and starts Uvicorn on 5000.
- Docker forwards host 8080 → container 5000.
- http://localhost:8080/health returned a healthy response.


Lessons from Debugging

- docker run does not automatically load a local .env file. Supply --env-file .env or -e PORT=5000.
- os.getenv reads the process environment; it does not read .env files itself.
- For Docker's --env-file, write PORT=5000 without spaces around the equals sign.
- Changing values supplied through --env-file requires creating a new container, not rebuilding the image.
- Code or Dockerfile changes require rebuilding the image and creating a new container.
- There is no need to delete the old image before rebuilding with the same tag.
- --rm automatically removes the container when it exits; it does not remove the image.


Recall Questions

1. Why use Artifact Registry?
   To make built images available beyond our laptop for deployment.

2. Artifact Registry versus Cloud Run?
   Artifact Registry stores images; Cloud Run runs applications from them.

3. Cloud Run versus GKE?
   Cloud Run handles infrastructure for us. GKE provides Kubernetes features and more control.

4. Why environment variables?
   To change runtime configuration while reusing the same application image.

5. What does -p 8001:8080 mean?
   Forward host port 8001 to container port 8080.
   The application must already be listening on container port 8080.

DAY 12 - Environment variables and Cloud Run configuration
Project: 01-python-fastapi

1. Environment variables and PowerShell
Environment variables supply runtime settings without changing application code.
Our .env contained PORT=5000. APP_VERSION and APP_ENV came from the
PowerShell session used to launch Python:

$env:APP_VERSION="3.0"
$env:APP_ENV="development"

Python reads its process environment with:
os.getenv("APP_VERSION")
os.getenv("APP_ENV")

The application returned 3.0 / development. A child process inherits the
session environment when launched. .env is a convenient text file, not a
requirement for every variable. os.getenv() does not itself load .env.

2. Docker -e (exact command from the conversation)
docker run --name cn-employee-api-v3 `
  -e APP_VERSION=3.0 `
  -e APP_ENV=development `
  -p 8080:8000 employee-api:v3

-e sets a variable inside that container. -p 8080:8000 maps host port 8080
to container port 8000. PowerShell session variables are not automatically
copied into a Docker container by this command.

3. Same image, different container configuration
Both containers used employee-api:v3:
Container A: APP_VERSION=3.0, APP_ENV=development
Container B: APP_VERSION=3.1, APP_ENV=dev
Each container reads its own environment. Same image + different runtime
configuration can produce different behaviour. APP_VERSION is a setting;
changing it does not rebuild or change the image tag.

4. --env-file .env (exact examples from the conversation)
docker run `
  -e APP_VERSION=3.2 `
  -e APP_ENV=test `
  -e ABC=123 `
  -e XYZ=456 `
  employee-api:v3

docker run --env-file .env employee-api:v3

We CAN use many -e arguments. --env-file is easier to manage when there
are many variables. It reads definitions from the named file into the
container environment. The examples are equivalent only if .env contains
the same assignments. A file containing only PORT=5000 does not supply
APP_VERSION or APP_ENV. .env is not specific to Docker.

5. Build, tag, push and Artifact Registry
Build packages the application into employee-api:v3. Tag gives the local
image its Artifact Registry address. Push uploads it to that registry,
where Cloud Run can retrieve it.
