3. Artifact Registry

Created Docker Artifact Registry repository:

    Repository: employee-api
    Region: europe-west2
    Format: Docker

Artifact Registry is where the Docker image is stored in GCP.

Important:

Docker itself creates/runs the image locally.

Artifact Registry stores the built image remotely so that
cloud services such as Cloud Run can deploy it.

Flow:

    Local Docker Image
            |
            | docker push
            v
    GCP Artifact Registry


4. Configure Docker Authentication

Docker must authenticate with GCP before it can push images
to Artifact Registry.

Configured Docker credential helper:

    gcloud auth configure-docker europe-west2-docker.pkg.dev

This updated Docker configuration so that Docker can use
Google Cloud credentials for:

    europe-west2-docker.pkg.dev

Without this authentication, Docker push will fail because
Artifact Registry is not an anonymous/public Docker registry.


5. Push Docker Image to Artifact Registry

Image path:

    europe-west2-docker.pkg.dev/cloud-genai-learning/employee-api/employee-api:latest

Pushed image:

    docker push europe-west2-docker.pkg.dev/cloud-genai-learning/employee-api/employee-api:latest

Push completed successfully.

Artifact Registry then showed the employee-api image with
the "latest" tag.

Important:

The image digest (sha256:...) uniquely identifies the exact
contents of an image.

Tag:

    latest

is a friendly/movable name.

Digest:

    sha256:...

identifies the exact immutable image content.


6. Cloud Run

Cloud Run is a fully managed service for running containers.

Instead of manually creating:
- VM
- Kubernetes cluster
- Pods
- Load balancer

we give Cloud Run our container image and Google manages
the underlying infrastructure.

Created Cloud Run service:

    Service: employee-api
    Region: europe-west2 (London)

Selected the existing employee-api container image from
Artifact Registry.


7. Cloud Run Authentication

Selected:

    Allow public access

This allows us to access the learning API directly from the
browser without authentication.

This is useful for the current learning exercise.

For a real production application, public access should only
be enabled when the API is intentionally public. Otherwise
IAM/authentication should be configured.


8. Billing Mode

Selected:

    Request-based

With request-based billing, CPU is primarily allocated while
the container is processing requests.

This is suitable for our small learning API.


9. Autoscaling and Cost Protection

Selected:

    Auto scaling

Configured:

    Minimum instances = 0
    Maximum instances = 1

Minimum = 0

Cloud Run can scale the application down to zero instances
when there are no requests.

This helps avoid keeping an instance running unnecessarily.

Maximum = 1

For our learning project, only one instance is allowed.

This prevents accidental traffic from causing the application
to scale to many instances.

These settings help control cost during learning.

Important:

Free-tier allowances do NOT mean that every GCP resource is
guaranteed to cost £0.

Always:
- keep learning resources small
- configure sensible scaling limits
- monitor billing
- remove unused resources


10. Ingress

Selected:

    All

This allows requests to reach the Cloud Run service directly
from the internet.

Combined with:

    Allow public access

we can access the FastAPI application from the browser.


11. Container Port

Configured Cloud Run container port:

    8080

Cloud Run sends incoming requests to the container on this port.

Our application does not need the public URL to contain:

    :8080

because 8080 is the INTERNAL container port.

Public request flow:

    Browser
       |
       | HTTPS
       | Port 443
       v
    Cloud Run
       |
       | Internal routing
       v
    Container :8080
       |
       v
    FastAPI / Uvicorn

Therefore:

    https://employee-api-....run.app

is correct.

We do NOT use:

    https://employee-api-....run.app:8080


12. PORT Environment Variable

Locally, .env may contain:

    PORT=5000

But Cloud Run provides its own PORT environment variable.

For this deployment Cloud Run uses:

    PORT=8080

Therefore the application should not depend on a permanently
hardcoded port.

The application should read the runtime PORT value.

This allows the same application/container to run in
different environments.

Example:

Local:

    PORT=5000

Cloud Run:

    PORT=8080

14. Service Account

Selected:

    Default compute service account

The service account represents the identity used by the
Cloud Run revision when it needs to access other GCP
resources.

For this simple learning API, the default service account
is sufficient.

For production systems, we should normally create a
dedicated service account and grant only the permissions
required by the application.

This follows the principle of least privilege.


15. Encryption

Selected:

    Google-managed encryption key

Google manages the encryption keys automatically.

Did NOT select:

    Cloud KMS key

Customer-managed KMS keys are useful when an organization
needs direct control over encryption keys, rotation,
permissions, etc.

Not required for this learning exercise.


16. Binary Authorization

Binary Authorization was NOT enabled.

Binary Authorization can be used to control which container
images are permitted to be deployed.

This is a more advanced security/deployment topic and is not
required for the current learning exercise.


17. Cloud Run Deployment

Cloud Run successfully created:

- Service
- Revision
- Traffic routing

Revision created similar to:

    employee-api-00001-...

A revision represents a particular deployed version/configuration
of the Cloud Run service.

Future deployments can create new revisions.

This allows Cloud Run to support:
- deployment history
- traffic splitting
- rollback to previous revisions

23. Cloud Run vs Kubernetes / GKE

Important distinction:

Cloud Run does NOT expose Kubernetes Pods for us to manage.

Cloud Run:

    Docker Container
          |
          v
    Cloud Run Revision
          |
          v
    Managed Instance(s)

Google manages the underlying infrastructure.

Therefore we don't run:

    kubectl get pods

for this Cloud Run service.

With GKE/Kubernetes later:

    Docker Image
         |
         v
    Kubernetes Deployment
         |
         v
    Pod(s)

and we will use commands such as:

    kubectl get pods
    kubectl logs <pod-name>

Quick Revision Questions:

1. What is Artifact Registry?
   -> GCP service used to store container images/artifacts.

2. Why run gcloud auth configure-docker?
   -> Allows Docker to authenticate with GCP Artifact Registry.

3. What does docker push do?
   -> Uploads the local Docker image layers to the registry.

4. What is Cloud Run?
   -> Fully managed service for running containers without
      managing servers or Kubernetes.

5. Why minimum instances = 0?
   -> Allows the service to scale to zero when unused.

6. Why maximum instances = 1 for this project?
   -> Limits scaling and helps protect against unexpected
      learning-project cost.

7. Why is 8080 not in the public URL?
   -> 8080 is the internal container port. Cloud Run exposes
      the service publicly over HTTPS/443.

8. What is a Cloud Run revision?
   -> A deployed version/configuration of the Cloud Run service.

9. Where are application logs viewed?
   -> Cloud Run -> Service -> Observability -> Logs.

10. Does Cloud Run give us Kubernetes Pods to manage?
    -> No. Cloud Run manages the underlying infrastructure.
       Pods become relevant when learning GKE/Kubernetes.
